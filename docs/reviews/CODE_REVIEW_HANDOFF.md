## P1 — Correctness and data integrity

### SF-01 — Reappraising the last citation deletes the remainder of the review

**Location** `sourcefidelity-batch/scripts/reappraise_apply.py:52–58` and `:109–146` (`block_span`, `apply_review`). See also the count rendering in `sourcefidelity-batch/scripts/render_review.py:145–149`.

**Observed — reproduced.** When there is no following citation heading, the citation span extends to end of file. The normal rewrite replaces everything from the judgment line to the end of that span. Updating the final citation in a synthetic review removed the bibliography and audit sections, and the old occurrence-count line stayed unchanged. The same span can contain uncited passages and any existing reappraisal log.

**Acceptance criteria.** Reappraise both a middle citation and the final citation in a review generated by the renderer. Preserve unaffected sections and prior log rows, append one row for each changed judgment, and reconcile the visible counts with `summary.json`. Validate the completed rewrite before replacing the review, ledger, and summary.

### SF-02 — A reappraisal can attribute text from an old copy to a new PDF

**Location** `sourcefidelity-batch/scripts/reappraise_prepare.py:145–163` and `:225–234` (`main`).

**Observed — reproduced with mocked identity matching.** The task carries the newly supplied path but reuses any existing extraction associated with the registry record or its source object. The synthetic task identified the new PDF while pointing its passage lookup to text from the old copy. A different edition can have different text, pagination, or chapter coverage.

**Acceptance criteria.** Use two copies with distinct hashes, text, and page maps. The task for the new copy points to an extraction whose recorded hash matches that copy, and its windows, page map, and chapter coverage come from that extraction. Identical copies can reuse the verified extraction. If extraction fails or the edition differs, propagate the applicable limitation to the task and report.

### SF-03 — Validation accepts missing occurrences and empty findings

**Location** `sourcefidelity-batch/scripts/validate_inventory.py:90–111` and `:130–144` (`check_disposition`), `sourcefidelity-batch/scripts/render_review.py:41–51` and `:361` (`validate`, `render_summary`).

**Observed — reproduced.** A synthetic candidate marked `confirmed` passed strict validation with zero final occurrences and no coverage block. Confirmed dispositions return without checking for a corresponding final entry, and absent coverage produces a warning even in strict mode. The renderer accepts an empty findings object and defaults its status to `complete`.

**Acceptance criteria.** Strict validation rejects confirmed candidates without corresponding final entries and missing or incomplete paragraph coverage. Rendering reconciles final C/R/W/U IDs against the validated inventory and checks evidence requirements. Empty findings are accepted only when the validated inventory is genuinely empty and processing status is explicit.

### SF-04 — Batch consumers silently omit valid paper IDs

**Location** `sourcefidelity-batch/scripts/prepare_batch.py:37–43` (`paper_id_for`), `sourcefidelity-batch/scripts/batch_report.py:85–96` (`summary_files`), `sourcefidelity-batch/scripts/audit_tasks.py:22–35` (`paper_ids`). Similar filters appear in acquisition, batch validation, report alignment, and cohort analysis.

**Observed — reproduced.** Preparation can emit `essay` for `essay.docx`, while downstream commands discover papers using `P*` or `paper-*`. In a synthetic batch containing `essay` and `P1`, report discovery returned only `P1`. Validation can therefore approve the subset it found.

**Acceptance criteria.** Use a shared manifest-based paper index and retain a path for legacy batches. A batch containing `essay.docx` and a participant-number submission carries both papers through task generation, validation, acquisition, and reporting. A missing summary for a scheduled paper is visible in the batch outcome.

### SF-05 — Source keys can conflate distinct works before identity checks

**Location** `sourcefidelity-batch/scripts/acquisition_list.py:60–76` (`key_from_entry`), `sourcefidelity-batch/scripts/source_registry.py:237–269` (`candidate_sources`, `canonicalise`).

**Observed — key collision reproduced.** Two same-author, same-year references with titles beginning “Digital Media and Cultural …” and different DOIs produced the same key. The registry groups entries by that key before verifying identity and uses one representative. This can attach one work’s PDF, page scope, or retrieval status to another.

**Acceptance criteria.** Distinct verified DOIs, ISBNs, or materially different editions remain distinct. Same-author and same-year titles with the same prefix stay separate when the remaining fields differ. Formatting variations of the same verified work still resolve to one identity, with existing aliases retained where practical.

### SF-06 — Restricted evidence windows extend outside the cited chapter

**Location** `sourcefidelity-batch/scripts/make_task.py:154–167` (`windows`), `sourcefidelity-batch/scripts/lookup.py:64–83`.

**Observed — reproduced for task windows.** The code checks the match’s starting page, then slices surrounding text from the full extraction. A hit labeled printed page 10 contained text from the preceding chapter on page 9. The lookup CLI uses the same range-check-then-slice pattern.

**Acceptance criteria.** Test hits near both boundaries of an allowed range through task generation and the lookup CLI. Returned text stays within permitted pages, and a match spanning a disallowed boundary is discarded. Each evidence window carries its source identity and accurate page provenance.

### SF-07 — Confirming a source can leave the fabrication flag in place

**Location** `sourcefidelity-batch/scripts/reappraise_apply.py:201–243` (`apply_summary`).

**Observed — reproduced.** Reappraisal updates retrieval to `retrieved` but leaves the previous identity outcome and the nonexistence and unverifiability lists untouched. A synthetic source remained `nonexistent_as_cited` after becoming `retrieved`, and still contributed to the fabrication flag.

**Acceptance criteria.** When a newly supplied copy resolves the previously disputed identity, update the identity outcome, access state, affected finding lists, and dependent flags together. Preserve the former judgment in the audit history. Test that an ambiguous or different edition leaves the unresolved identity finding in place.

## P2 — Security, reliability, and reporting

### SF-08 — A copy-only installation silently bypasses PDF OCR and provenance

**Location** `README.md` (Requirements and Installation), `sourcefidelity-review/scripts/word_count.py:99–136` and `:261–275` (`pdf_extract`, `pdf_blocks`), `sourcefidelity-batch/scripts/authorship_signals.py:41–45` and `:371–387`, `sourcefidelity-batch/scripts/prepare_batch.py:103–110`.

**Observed — reproduced without the expected virtual environment.** The README instructs users to copy the skill directories, while OCR-backed word counting and PDF authorship analysis require a hard-coded `.venv/bin/python`. A blank synthetic PDF fell back to native extraction, returned zero words, and had no explicit `counts_available` value. Candidate extraction shares the word-count extraction path, and the batch paper record omits page-level extraction status.

**Acceptance criteria.** Document and verify a clean installation with a supported interpreter and dependencies. Exercise native-text and image-only PDFs. When OCR or a parser is unavailable, preserve unavailable or partial counts, OCR provenance, and affected pages through the review and batch summary.

### SF-09 — Student text and fetched pages lack an explicit trust boundary

**Location** `sourcefidelity-batch/WORKER_CONTRACT_REVIEW.md:3` and `:32–41` (Inspect supplied web sources).

**Observed — static review.** The contract exposes untrusted student text and source excerpts to the worker and directs it to open supplied URLs. It does not spell out that instructions found in documents or responses are evidence only. Destination restrictions depend on the host fetch tool. The security impact depends on what tools and credentials the worker can access.

**Acceptance criteria.** In a worker test with synthetic documents and mocked fetch responses, embedded instructions have no effect on task scope, tool use, disclosure, or output destinations. Restrict the worker to the read-only tools it needs. Enforce public-web destination rules on the initial request and redirects, and keep student text and credentials out of requests.

### SF-10 — Task-controlled paths can direct reappraisal writes outside the batch

**Location** `sourcefidelity-batch/scripts/reappraise_apply.py:256–267` and `:287–298` (`main`).

**Observed — static review.** The apply CLI takes `paper_id` from task JSON and joins it directly to the batch root. It does not validate membership in the batch or check the resolved paths of the destination files. A modified or imported task, or an existing symlink, can redirect a write. The concern applies when the runner can access the redirected destination.

**Acceptance criteria.** Require a valid manifest paper ID and check that every resolved destination for review, backup, ledger, and summary stays inside that paper’s batch directory. Tests reject invalid IDs or destinations redirected outside the batch before any artifact is created or changed.

### SF-11 — One observed folio can make an inferred page map look reliable

**Location** `sourcefidelity-review/scripts/page_map.py:129–160` (`infer_offset`, `build`), `sourcefidelity-review/scripts/prepare_source.py:216–227`.

**Observed — reproduced.** The offset’s coverage is the fraction of detected folios that agree. A single observed folio therefore yields 100 percent coverage. The caller treats that as sufficient to populate printed numbers throughout the PDF, including where there may be inserts, resets, or no visible folio.

**Acceptance criteria.** Label observed and inferred folios distinctly. Require corroborating folios before inferring a continuous offset, preserve visible folios over extrapolation, and leave ambiguous pages explicitly unmapped. Test single-observation, stable-offset, and pagination-reset fixtures.

### SF-12 — Cohort S1 includes ineligible references in its denominator

**Location** `sourcefidelity-batch/scripts/authorship_signals.py:683–698` (`cohort`), `sourcefidelity-batch/scripts/render_review.py:308–313` (`render_summary`), `sourcefidelity-batch/BATCH_ADDENDUM.md:219–224`.

**Observed — reproduced.** The cohort code divides by all references. With three eligible findings among five searched references and ten total references, the code reported 0.30 and left S1 off. Under the documented searched-reference denominator, the share is 0.60 and S1 fires. The renderer has a separate S1 calculation, which can produce a different result and does not consistently filter the numerator.

**Acceptance criteria.** Use one shared calculation with eligibility applied to both numerator and denominator at a consistent unit of counting. Confirm identical output from per-paper and cohort reporting. Include partial or unsearched reference fixtures and make eligibility limitations explicit when reading older summaries.

### SF-13 — Dry run queries the provider and writes its cache

**Location** `sourcefidelity-batch/scripts/enrich_registry.py:288–369` (`enrich`).

**Observed — reproduced with a mocked provider.** An eligible chapter caused a provider call and a cache write during `--dry-run`. The flag guards the final registry and sidecar writes but allows requests, in-memory record updates, and cache writes inside the loop.

**Acceptance criteria.** Dry run reports the planned eligible records and lookup counts, with zero provider calls and zero filesystem writes. Normal mode retains the same lookup and cache behavior.

### SF-14 — Extraction failure returns success with missing or stale candidates

**Location** `sourcefidelity-batch/scripts/prepare_batch.py:88–110` (`main`).

**Observed — reproduced for a missing candidate file.** A malformed DOCX returned exit code zero and produced a paper record pointing at a `candidates.json` file that was never written. The exception branch builds a fallback object in memory. On reruns it can also leave an earlier candidate file available to downstream commands.

**Acceptance criteria.** A failed extraction leaves an explicit failure record consumed by downstream commands. Test a fresh malformed DOCX and a previously valid paper whose extraction now fails. Neither produces a review from absent or stale candidates, and the batch report still accounts for the failed paper.

## Optimization and maintenance

### OPT-01 — Extract each paper once

**Location** `sourcefidelity-batch/scripts/prepare_batch.py:83–100` and `sourcefidelity-batch/scripts/render_review.py:440–443`.

Word counting, candidate generation, and authorship profiling independently parse the same input. Rendering can profile it again. Share an extraction keyed by input hash and extraction settings. Preserve the page boundaries, OCR source, and missing-page metadata required by each caller. Check that the normal pipeline performs a single compatible extraction and that changing the file or extraction settings invalidates it. Measure elapsed time and memory on a representative synthetic batch.

### OPT-02 — Precompute cohort comparison sets

**Location** `sourcefidelity-batch/scripts/authorship_signals.py:750–765`.

The pairwise loop repeatedly normalizes sentences and constructs heading and n-gram sets. Prepare those sets once per paper, then compare them. Preserve the reported overlaps and thresholds. Benchmark processing time and peak memory before considering an inverted index or changing the pairwise algorithm.

### OPT-03 — Consolidate word counting and the review protocol

**Location** The three `scripts/word_count.py` files and the three `REVIEW_PROTOCOL.md` files in the skill directories.

Both sets of copies were byte-identical at the reviewed revision, but the copied word-count scripts look for OCR files relative to their own directory. Maintain a single implementation with thin entry points where required, and maintain one canonical review protocol or generate checked copies during packaging. Verify all three entry points using the documented sibling-directory installation.

### REUSE-06 — Separate failed searches from completed negative searches (SF-07, SF-12)

### REUSE-08 — Versioned reappraisal over structured records (SF-01, SF-03, SF-07)

## Review improvements from unfinished application guidance

These are additions to consider for the skills. Application status reflects the guiding documents and targeted source inspection at the application revision above. Some proposals extend a narrower implementation already in the app or formalize a manual rule already in the skill. The skill changes below are recommendations, with synthetic cases to establish the intended behavior before rollout.

### GUIDE-01 — Record what each citation is doing before judging it

**Application status.** The app recognizes further-reading markers and some evaluative uses. It has an example-of-research path and separates some writer-owned material. The roadmap still calls for checking whether explicit contrast citations represent the opposing position accurately, whether further-reading sources address the named topic, and how to isolate the source’s proposition inside the student’s application. See `ROADMAP.md:22`, `:31–32`, `:121–122`, and `app/services/citation_use_router.py:239–311`.

**Add to the review.** Keep the full student statement verbatim. Identify the exact words attributable to each source and record whether the source supplies a factual claim, example, explicit opposing view, conceptual framework, or further reading. For an explicit contrast, check whether the cited source takes the position the student says it takes. For an application, check the cited concept separately and describe the student’s use of it. For further reading, check topic relevance where coverage permits and keep that result separate from evidentiary support. Record role and scope per source, since a single citation group can serve several functions.

**Acceptance examples.** A citation explicitly naming the opposite view can be used accurately. A source defining a framework can support the definition while the student’s application remains their analysis. A relevant further-reading source receives a relevance note without an accuracy judgment. An ambiguous signal stays unresolved.

### GUIDE-02 — Distinguish a reported view from an explicit contrary position

**Application status.** The roadmap and state document identify this as an open Judgment distinction. The code guards against assigning explicit third-party speech to the cited author, but a decisive attribution conflict can still produce `contradicts`. The skill’s main protocol already tells reviewers to examine voice and endorsement. Its batch worker contract has no separate field for the distinction. See `ROADMAP.md:120`, `STATE.md:554`, `app/services/facet_evidence_judgment.py:1602–1620` and `:1717–1729`, and `sourcefidelity-review/REVIEW_PROTOCOL.md:217–225`.

**Add to the review.** For a material attribution issue, record who spoke, how the cited author presents that view, and whether the author expresses an incompatible position. Keep any secondary-citation issue separate from the assessment of the proposition. For example, where a cited author quotes an interviewee who takes the stated view, the review can explain the partial match and the speaker error. Reserve substantive contradiction for affirmative evidence of an incompatible position on the specified issue.

**Acceptance examples.** Test neutral reporting, explicit endorsement, explicit disagreement, and uncertain voice. The report highlights the correct speaker, and an explicit disagreement keeps its stronger finding.

### GUIDE-03 — Check explicit claims about recency and the research literature

**Application status.** The app can judge whether a cited work is an example of the research described. Its example-of-research prompt sets aside recency and other claims about the body of literature. A separate publication-date check is deferred. See `ROADMAP.md:123` and `app/services/facet_evidence_judgment.py:177–190`.

**Add to the review.** For a statement such as “all three cited studies were published in the previous five years,” record the time window, its basis, and the verified dates of each cited work. For vague “recent” claims with no established time window, list the dates and disclose the ambiguity. A set of examples can establish that some research fits a description. Claims about prevalence, growth, or what most research does require evidence appropriate to that broader scope.

**Acceptance examples.** A work with a verified date outside an explicit five-year window is identified. “Recent” without a defensible cutoff is described without a mismatch finding. Three matching examples cannot by themselves verify that most research takes the same approach.

### GUIDE-04 — Record what a split scan actually covers

**Application status.** The app already uses chapter continuity and crop checks. Automatic extent recognition for clipped folios and paired crops remains deferred. The skill already has the manual inspection rule, but the result can be made auditable in the task and ledger. See `ROADMAP.md:20`, `app/services/completeness_checker.py:254–262`, and `sourcefidelity-review/REVIEW_PROTOCOL.md:49–62`.

**Add to the review.** For a difficult scan, preserve observations for the titled opening, chapter-owned ending or references, continuity across paired fragments, and boundary of the next work. Record which pages are present, which are partly cropped, and which may be missing. Keep identity, component completeness, and extraction quality separate. Use the visible passage for a check it directly establishes and disclose the gap for judgments requiring wider coverage.

**Acceptance examples.** Test a complete chapter preceded by collection front matter, a split scan with duplicate overlap and clipped folios, and copies with a missing body page or cropped passage. Evidence for an intact excerpt remains usable within its scope.

### GUIDE-05 — Allow a scoped human source confirmation with an audit record

**Application status.** The app supports a narrower edition answer. The broader design for independently confirming work identity, edition/component, and completeness is approved for later implementation. The skill already directs reviewers to ask about ambiguous matches, but its fast reappraisal path has no equivalent structured decision record. See `ROADMAP.md:21`, `ARCHITECTURE.md:218–246`, `app/services/personal_edition_answer.py:28–44`, and `sourcefidelity-reappraise/REAPPRAISAL_PROTOCOL.md:45–55`.

**Add to the review.** When a consequential uncertainty remains, allow the reviewer to record a separate answer for each applicable dimension, bound to the exact file hash and the affected reference. Preserve the automatic observations and any unanswered questions. Carry the confirmation into the reappraisal log and limit its reuse to the recorded work, edition, and component. Finding identity alone leaves page coverage and text quality to be established.

**Acceptance examples.** Confirming a chapter leaves whole-book completeness unresolved. Changing the file requires a new decision. A confirmed translation remains a translation, with its own wording and locators. The successor review records both the earlier uncertainty and what the human confirmation resolved.

### GUIDE-06 — Retrieve across languages while quoting the original

**Application status.** The app has a whole-source route for eligible other-language texts that fit its input budget and a separate translation path for evidence display. Building a reusable translation index for longer texts is deferred. The skill currently asks reviewers to try relevant language variants. See `ROADMAP.md:111–112`, `app/services/cross_language_whole_source.py:156–186`, and `sourcefidelity-review/REVIEW_PROTOCOL.md:213–215`.

**Add to the review.** Start with native-script and translated query variants. If a longer source still needs a translation index, bind each translated segment to the original source hash, page, and text span. Use translation to locate passages. The review quotes the original, provides its locator, and labels any accompanying translation. Add a longer-source index only if a separate evaluation shows that it retrieves materially better evidence using an authorized local or approved workflow.

**Acceptance examples.** A cross-language query locates the correct original sentence even when its translation uses different wording. A mistranslated negation cannot produce a finding without verification against the original. A changed edition invalidates the index.

### GUIDE-07 — Make intermediary-paraphrase comparisons inspectable

**Application status.** The roadmap defers bounded comparison with intermediary texts beyond existing patchwriting checks. The skill already asks reviewers to check for copied published paraphrases. The opportunity is to carry the comparison through the worker and renderer with enough evidence to inspect. See `ROADMAP.md:137` and `:164`, and `sourcefidelity-review/REVIEW_PROTOCOL.md:256–266`.

**Add to the review.** On a specific lead and where the texts are available, record the student passage, the intermediary passage, and the cited original with their locators. Explain the distinctive wording, sequence, or shared unusual detail that ties the passages together. Give generic field terminology and commonly reused definitions less weight. When one text is unavailable or the overlap has a plausible shared origin, record the limit and separate verified attribution problems from conclusions about copying.

**Acceptance examples.** A distinctive phrase and unusual error shared with a published intermediary can be inspected side by side. Standard terminology alone produces no copying finding. A missing source leaves a specific coverage limitation.

**Priority for a first pass.** Start with GUIDE-01 through GUIDE-03 in the protocol and worker contract. These changes refine what the reviewer checks and can be tested on small, offline examples. Add GUIDE-04 and GUIDE-05 alongside the source-binding and versioned-reappraisal work. Treat GUIDE-06 and GUIDE-07 as bounded extensions with dedicated evaluation.
